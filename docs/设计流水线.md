# 设计流水线

> 本文讲**所有设计工种共用的那套流程**。工种自己的阶段表在 `.design/skills/<工种>/SKILL.md`，
> 全量清单见 [工种全景](工种全景.md)。规则文件与本文不一致时，**以技能目录里的文件为准**。

---

## 1. 三层结构

| 层 | 放在哪 | 管什么 |
|---|---|---|
| **引擎层** | `.design/rules/` | 交互节奏、状态机、收口、评审、来源、人格、全工种红线 |
| **工种层** | `.design/skills/<工种>/SKILL.md` | 本工种的阶段表、产物、门禁、参考路由 |
| **入口层** | `/design-router`、`/design-any` | 跨工种分流、长尾兜底 |

为什么要这样分：改一次公共门禁只动 `rules/` 一处，不用同步 19 份工种技能；
工种技能只写「我们这行到底多做哪几步」，不重复红线。

---

## 2. 端到端时间线

```text
第 0 阶段 确认现状  ──→  一次一问 / 决策树  ──→  收敛
   │                                              │
   │ 拿不到现状就停，不 best-guess                 ▼
   │                                    对话内出结论卡片
   │                                              │
   │                                    落盘 00-summary.md (analyzing)
   │                                              │
   │                                       ⛔ 停下来等人确认
   │                                              │
   └────────────────────────── 人确认 ──→  producing
                                                 │
                                    按工种阶段表逐阶段生产
                                    上一阶段 confirmed 才进下一阶段
                                                 │
                                          reviewing
                                                 │
                       AI 自检 → 独立评审 → 用户审核 → 回退重跑
                                                 │
                                    人确认 → confirmed → delivered
```

**两个硬停点**（AI 不得自行推进）：

1. `analyzing → producing`：简报 / 结论卡未经人拍板，不许出稿、不许写「已生成完成」；
2. `reviewing → confirmed`：最终产物未经人确认，不许宣布交付。

---

## 3. 第 0 阶段：先确认现状

每个工种的第 0 步都叫「确认现状」，只是问的东西不同：

| 域 | 必问 |
|---|---|
| 数字产品 | 现成产品 / 设计系统 / 组件库 / 品牌规范 / 参考稿 / 技术栈 |
| 平面品牌 | 媒介 / 尺寸 / 品牌规范 / 交付格式 / 字体与素材授权 |
| 空间与实体 | 场地 / 尺度 / 材料 / 工艺 / 法规与资质约束 |
| 商业与新兴 | 平台规则 / 商品或业务信息 / 现有素材 / 合规禁用项 |

- **一次只问一个**最该问的问题，附一句「为什么问」；回答决定下一个问题（决策树），不按文档顺序机械推进。
- 有安全默认值的缺口直接采用，标 `[默认值·可否决]`，**收口时一次性列出**让用户否决，不占提问额度。
- 用户口述、粘贴、截图、命令行参数**都算已回答过**，不重复问；原文按《产物与来源规范》§6 原样存 `sources/`。
- 拿不到现状就停。**不许 best-guess 视觉方向、品牌、对外承诺与业务规则**——这是本包最容易破也最要紧的一条。

### 三种输入档位

| 档位 | 何时用 | 行为 |
|---|---|---|
| Guided | 只有模糊想法，或明确要「带我一步步来」 | 默认，一次一问 |
| Context dump | 用户贴了一大段素材 | 归一成条目池，跳过已覆盖的，只追问真缺口 |
| Best guess | 信息不全但足以起草 | 逐行标 `[假设]`；**涉及视觉方向 / 品牌 / 对外承诺 / 无上游产物时禁用** |

## 4. 双状态机

### 驱动卡（一条流水线一条状态线）

写在 `.design/artifacts/<feature>/00-summary.md` 的 frontmatter `status`：

```text
draft → analyzing → producing → reviewing → confirmed → delivered
          ↑____________|          ↑___________|
              打回                    打回
```

| 状态 | 含义 | 谁推进 |
|---|---|---|
| `draft` | 建立，未开始 | AI |
| `analyzing` | 问答收敛完成，**待人确认** | AI |
| `producing` | 生产主产物 | **人类确认后** |
| `reviewing` | 提交评审 | AI |
| `confirmed` | 最终产物确认 | **人类确认后** |
| `delivered` | 已交付 | AI |

### 单产物状态

每个产物自己的 frontmatter：`draft → proposed → reviewing → confirmed → delivered`。
**上一阶段 `confirmed` 才进下一阶段**；门禁不过退回对应上游，不跳级，回退原因写进驱动卡。

状态写在文件里，所以**新会话读 status 就知道断点在哪**，不重复访谈。

## 5. 各域阶段表

工种技能里的流水线表都一样是 8 步，差异在中间几步。

### 数字产品（以 UI 设计师为例）

`现状确认 → 设计简报与目标 → 信息架构与页面结构 → 视觉方向与组件清单 → 界面稿与状态覆盖 → 组件规格与令牌 → 评审与走查 → 交付与验收`

特色门禁：8 类状态（`默认 / 加载 / 空 / 单条 / 极多 / 超长 / 错误 / 权限不足`）缺一类退回；
涉及界面按 WCAG 2.2 AA 逐条给实测值与条款号。

### 平面品牌（以品牌 / VI 设计师为例）

`现状确认 → 定位关键词 → 标志方向 → 色彩字体 → 应用矩阵 → 手册 → 资产导出`

特色门禁：字体商用 / 嵌入 / 分发授权逐项核验；图片素材记来源与许可；交付格式、出血、色彩模式明确。

### 空间与实体（以 3D 建模与渲染为例）

`现状确认 → 镜头构图 → 模型拓扑 → 材质贴图 → 灯光色彩 → 渲染参数 → 后期导出`

特色门禁：只交付**可复现的配置**（镜头脚本 / 材质灯光 / 渲染参数表），不假装交付成片；
施工图 / 打样 / 结构验算一律声明给不出。

### 商业与新兴（以电商视觉设计师为例）

`现状确认 → 卖点排序 → 主图层级 → 详情页节奏 → 多尺寸 → 合规检查 → 导出`

特色门禁：平台规则与合规禁用项**不臆造条款号**，不确定标「待核验」。

### 长尾工种（`/design-any` 的 8 步）

`确认现状（含边界声明）→ 目标与约束 → 参考与竞品 → 结构/层级方案 → 2–3 个方向提案 → 收敛 → 规格与检查清单 → 交付与交接`

第 0 步必须先贴出边界声明：

```text
我能给你：需求简报、参考与竞品分析、方案方向、规格与检查清单、可评审文档。
我不能给你：施工图 / CAD / BIM、打样件、可印制原文件、材料与结构验算、资质报审。
```

详见 `.design/references/工种通用流水线.md`。

## 6. 全工种红线（违反即停）

| # | 红线 |
|---|---|
| 1 | 未确认不生产；不跳门禁、不把「停」包装成「完成」 |
| 2 | 不编造：审批人 / 数据 / 金额 / 期限 / 用户量 / 调研结论一律 `[缺失·阻塞]`；推断标 `[推断·待确认]` |
| 3 | 来源落盘：口述、粘贴、截图原样存 `sources/`，记出处与日期 |
| 4 | 授权核验：字体、图库、参考稿的商用 / 嵌入 / 分发范围拿不到就标待授权 |
| 5 | 可访问性：WCAG 2.2 AA，正文 ≥ 4.5:1、大字与焦点 ≥ 3:1、目标 ≥ 24×24 CSS px，逐条给实测值 |
| 6 | 状态完整性：8 类状态全覆盖，禁止「异常流程以此类推」 |
| 7 | AI 生成物排查：出图后过 `AI生成设计缺陷清单.md`，常见痕迹必须有品牌或场景理由 |
| 8 | 不假交付：给不出的实体产物如实说明 |
| 9 | 交付前四步：AI 自检 → 独立评审 → 用户审核 → 回退重跑 |

### 交付前四步

- **AI 自检**：对照「最初说的」和「最后给的」查漂移，结论写进驱动卡 `00-summary.md`，不只嘴上说。
- **独立评审**：派**只读**子智能体分 Spec / Standards 两轴，报告不合并不排序，0 个 🔴 才进用户审核。
  宿主无子智能体原语 → 另开新会话顺序两遍，**必须标注「降级模式」**。主会话自审不算。
- **用户审核**：明确请其逐条给意见，停下等待。
- **回退重跑**：改目标回 `analyzing`、改产物回 `producing`、改评审结论回 `reviewing`；回退要留痕，重跑后重新自检与重新请审。

## 7. 对话内展示

**文件是留档，对话是交付。** 结构、状态、视觉语言、组件规格、结论卡片、路由卡必须直接出现在对话里；
只给一个文件路径等同于没交付。需要看视觉稿时，优先给能在对话里直接显示的图，不甩 HTML 路径。

同时**不把内部术语摆给用户**：`§11`、`status: analyzing`、`frontmatter`、`dossier`、`门禁`、
`决策树`、工种 key 这些是实现细节，不该出现在对用户的措辞里。

---

## 8. 工种层怎么接这套引擎

`disciplines.json` 是单一事实源，每个 `core` 工种登记
`key / name / en / domain / tier / triggers / summary / pipeline / artifacts / references / sources`。
`build-disciplines.py` 由它生成工种的 `SKILL.md.tpl`，里面只写：

1. 定位与边界（不负责哪些相邻工种、跨工种交给 `/design-router`）；
2. 第 0 阶段要问的现状；
3. 8 步流水线表（输入 / 出口门禁 / 产物）；
4. 产物与状态；
5. 门禁红线；
6. 参考文件路由表（**按需加载**，不一次全读）；
7. 交付前四步。

改工种只改 JSON 再跑生成器，不要手改生成物；`build-disciplines.py --check` 会拦漂移。
