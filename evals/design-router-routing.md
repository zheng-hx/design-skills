# Eval: 跨工种分流 · 路由卡与依赖顺序

> **技能**: `/design-router`　**工种**: 入口　**目的**: 验证跨工种需求只分流不出稿、
> 输出带依赖顺序的路由卡、一次一问，且不把多工种产物揉成一份四不像。

---

## 输入（固定场景，原样投喂）

```text
/design-router 我们要做新品牌，官网和包装都得做。VI 定完再改落地页。
```

> 场景里**已经给了依赖顺序**（VI → 落地页），用来验证路由卡不重排、不并行出稿。

---

## 期望（可断言）

### 结构断言

- [ ] `[机器]` 输出路由卡，列「交付物 / 工种 / 命令 / 依赖」四列
- [ ] `[机器]` 至少拆出品牌 VI、官网落地页、包装三条，分属 `brand-design` / `web-design` / `packaging-design`
- [ ] `[机器]` 落地页标注依赖「品牌 VI 的色彩与字体」，且排在 VI 之后
- [ ] `[机器]` 只感知本次实际安装的工种；子集安装时不推荐未安装的命令
- [ ] `[机器]` 路由卡直接贴在对话里
- [ ] `[人判]` 依赖列写的是「谁的输出给谁当输入」，不是含糊的「需协调」
- [ ] `[人判]` 没有把三个工种合并成一份「品牌官网包装综合方案」

### 门禁断言

- [ ] `[机器]` 路由技能本身**不出稿**：不产出视觉方向、色板、组件规格、界面稿
- [ ] `[机器]` 一次只问一个最该问的问题，不一次性列全量问卷
- [ ] `[机器]` 未给出品牌规范 / 媒介尺寸 / 平台规则时标 `[缺失·阻塞]`，不编造
- [ ] `[机器]` 长尾需求指向 `/design-any`，core 需求指向对应工种，不硬接
- [ ] `[机器]` 不宣布「已完成全部分流并交付」，分流结论也要请用户确认

### 过程断言（看 `transcript.md`；没采集记「未采集」，不算失败）

- [ ] `[机器]` 首个问题围绕分流所需信息（是否已有品牌规范 / 本次范围 / 哪些先做），不先问配色偏好
- [ ] `[人判]` 不重复询问用户已经说过的依赖顺序

### 反例（出现即失败）

- 路由技能直接给出色板、字体、版式、界面稿
- 「三个一起做，我出一份综合稿」
- 把依赖顺序倒过来（先落地页再 VI）
- 推荐本次没安装的工种命令，却不说明未安装
- 编造品牌定位、行业案例、审批人、期限

```json
{"checks": [
  {"file": "*.md", "match": ["交付物", "工种", "命令", "依赖"]},
  {"file": "*.md", "match": ["brand-design|品牌", "web-design|网页|落地页", "packaging-design|包装"]},
  {"file": "*.md", "match": ["色彩|字体|品牌规范", "design-router|分流"]},
  {"file": "*.md", "if_match": "design-any", "then_match": "长尾|通用流水线|边界"},
  {"file": "*.md", "not_match": ["综合方案", "三个一起做", "我出一份", "色值\\s*#[0-9A-Fa-f]{6}"]},
  {"file": "*.md", "not_match": ["已交付全部", "已完成视觉稿", "行业惯例是"]}
]}
```

---

## 判定

| 结果 | 条件 |
|---|---|
| 通过 | 路由卡四列齐全、依赖顺序正确、路由技能 0 出稿 |
| 不通过 | 路由技能自己出了产物，或把多工种合并成一份 |
| 未跑 | `evals/runs/design-router-routing/` 无产物 |

> 依赖顺序断言是本评测的核心：跨工种任务最常见的失败不是漏做，而是**并行出稿后互相打架**。
