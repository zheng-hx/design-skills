# 技能行为评测（evals）

> 仓库里 `npm run check:all` 验的是「装得上、结构对、渲染保真、门禁拦得住」。
> 本目录验的是另一件事：**给一段真实的人话，技能的产出对不对**。

---

## 边界（先说清楚，避免误解）

- 本目录**不做自动审美评分**。「好不好看」只能人判。
- 机器断言只抓**结构 / 门禁 / 禁语 / 条件承诺**这类可机械判定的部分，抓不到「内容胡说」。
- 本包**没有** `run-evals.py` 判定器。评测是「固定输入 + 可断言期望 + 机器可判断言 JSON」，
  需要在装好技能的项目里真跑一遍，把产物放进 `evals/runs/<评测名>/` 后由人或外部判定器判卷。
- 没有产物的评测记「未跑」，**不算失败**，CI 不会因此变红。
- `evals/runs/` 是本地留证，不入库。

---

## 文件组织

| 文件 | 用途 |
|---|---|
| [triggers.md](triggers.md) | **触发层金标集**：30 条「用户会说」→ 期望技能，同时是人工回归清单 |
| [design-ui-state-coverage.md](design-ui-state-coverage.md) | UI 界面稿：8 类状态覆盖、可访问性实测值、未确认不生产 |
| [design-any-boundary.md](design-any-boundary.md) | 长尾工种：第 0 步边界声明、不假交付实体产物 |
| [design-router-routing.md](design-router-routing.md) | 跨工种需求：只分流不出稿、依赖顺序、不合并成四不像 |

格式固定：

```markdown
# Eval: <名字>
> **技能**: /<skill>　**工种**: <discipline>　**目的**: <验证什么>

## 输入（固定场景）        ← 原样投喂给技能的一段话
## 期望（可断言）
### 结构断言              ← 每条标 [机器] 或 [人判]
### 门禁断言
### 反例（出现即失败）
## 机器可判断言（JSON）    ← ```json 块，判定器读它
## 判定
```

**`[机器]`** = 可自动检查；**`[人判]`** = 人 / 评审子智能体判断，不自动打分。

JSON 断言支持的判据：

| 判据 | 语义 |
|---|---|
| `exists` | 文件（支持 glob）至少匹配到 1 个 |
| `sections` | 每个关键词都要出现在某个标题行 |
| `match` | 每个正则至少命中 1 次 |
| `not_match` | 任一正则命中即失败（禁语 / 反例） |
| `if_match` + `then_match` | 命中 A 就必须也有 B |
| `min_count` | `{pattern, min}`：命中次数不得少于 min |

## 怎么跑

**第 1 步 · 真跑技能**：把评测的「输入」原样投喂给装好技能的项目，产物拷到
`evals/runs/<评测名>/`，会话记录存 `transcript.md`（用于过程断言）。

**第 2 步 · 判卷**：对照 JSON 断言逐条判，结果写 `result.json`；
下一次再判时对比上一次，输出「🔴 新失败 / 🟢 新通过」——**防回归才是评测的价值**。

**第 3 步 · 触发金标集**：逐条投喂 `triggers.md` 的「用户会说」，看实际命中的技能对不对。
`npm run check-evals` 只做**词面与覆盖的静态校验**，不等于真跑模型看它选哪个技能。

---

## 为什么这几份评测最重要

1. **UI 状态覆盖**：AI 最容易只画理想态，把异常流程写成「以此类推」；
2. **长尾边界**：AI 最容易把方案文档说成「已完成室内设计」，这是本包最在意的**假交付**；
3. **路由**：跨工种需求最容易被揉成一份四不像，或跳过依赖顺序直接出稿。
