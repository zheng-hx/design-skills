# 触发层金标集

> 30 条「用户会说的原话」→ 期望技能。回答两个问题：
> **覆盖**（期望技能存在且每个工种都有金标）、**分流**（长尾不该被 core 技能硬接）。
>
> `npm run check-evals` 静态校验本表：期望技能必须存在、19 个 core 工种 + 2 个入口必须各有一条金标。
> 这是**词面覆盖**校验，不是真跑模型；真跑方式是逐条投喂，看实际命中的技能。

## 易混淆边界（人工重点回归）

| 用户说 | 容易错选 | 应走 | 判据 |
|---|---|---|---|
| 「登录页太难用」 | `/ui-design`（改视觉） | `/ux-design` | 问题是流程 / 可用性，不是视觉层 |
| 「按钮点了没反应」 | `/visual-design` | `/interaction-design` | 行为与反馈机制 |
| 「整套品牌 + 官网 + 包装」 | 随便挑一个工种全做 | `/design-router` | 跨工种，先分流 |
| 「施工图帮我出了吧」 | 某个工种硬接 | 明确说明给不出 | 不假交付 |
| 「你定就行，直接出稿」 | 跳过收口 | 仍先出结论卡请确认 | 未确认不生产 |

## 加新金标的规矩

1. 期望技能必须写 `/<skill>` 形式，`npm run check-evals` 会校验它存在；
2. 新增 core 工种必须同步加一条金标，否则覆盖校验失败；
3. 加 extended 金标时，「期望技能」一律写 `/design-any`；
4. 若某条真跑时持续命中错误技能，先改 `disciplines.json` 的 `triggers` 与工种 `description`，
   跑 `build-disciplines.py` 重生成，再回来更新本表——**不要只改金标去迁就错误行为**。
