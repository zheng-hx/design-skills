# Update Design Skills — 更新本地设计师技能

> 设计师技能默认装在**用户全局工作台 `~/.design/`**，由 `/apply-design-skills` 生成、
> `/install-design-skills` 注册到各 AI 工具。**首次执行 = 初始化，重复执行 = 升级。**
> 用户只需说一句「更新技能」，本技能走完整条链路。

## 三层过期，顺序永远是 ① → ② → ③

| 层 | 是什么 | 在哪 | 谁更新 |
|---|---|---|---|
| **① 入口技能包** | `apply` / `install` / `update` 三个本技能文件 | 用户全局工具目录的软链源 = 技能源仓库 | 用户刷新源（git pull / 重新安装）后本技能重跑 |
| **② 共享工作台** | `~/.design/` 的规则 / 模板 / 参考 / 技能 / 注册表 | 用户主目录 `~/.design/` | 替换式重渲染 |
| **③ 工具注册** | 各 AI 工具**用户全局技能目录**的软链 | `~/.workbuddy/skills`、`~/.agents/skills` … | 扫描 + 对账（多退少补） |

> **① 没刷新，② 只能渲染出旧内容；② 没重渲染，③ 注册的是旧技能。**

---

## Step 0: 版本检测与分流（强制，先于任何写操作）

版本事实源：**`<apply-design-skills 技能目录>/VERSION`**（住在技能目录里，因为
`npx skills add` 只拷技能目录，仓库根的 `package.json` 带不过去）。

| `~/.design/` | `design.json` 的 `package_version` | 模式 | 行为 |
|---|---|---|---|
| 不存在 | — | **未初始化** | 只刷新①，然后**询问**是否初始化；不得擅自生成整套 `~/.design/` |
| 存在 | 缺失（早期版本） | **补档升级** | 备份 → 替换管理区 → 保留用户区 → 补版本戳 |
| 存在 | `< 当前版本` | **升级** | 备份 → 替换管理区 → 保留用户区 → 写新版本戳 → 输出对比 |
| 存在 | `== 当前版本` | **已最新** | **不写任何文件**，输出「已是最新」；仅用户明确要求才强制重渲染 |
| 存在 | `> 当前版本` | **拒绝** | 立即停止：工作台由更新版生成，请先升级技能包，**不得降级** |

读不到 `VERSION` → 按 `unknown` 处理，**如实报告技能包可能不完整**，不静默继续、不编版本号。
**当前版本必须从①刷新后的技能目录重读**——刷新前读到的是旧版本。

## Step 1: 刷新入口技能包（①）

**仓库地址从哪来（按优先级，不硬编码、不猜）**：

1. `~/.design/design.json` 中本包记录的 `source`（当初的安装地址，最可靠）；
2. 环境变量 `AI_DESIGN_SKILLS_REPO`；
3. 目标项目根 `skills-lock.json` 中本包记录的 `source`；
4. 都没有 → **明确报错并提示用户给出仓库地址**，不得编一个地址继续。

```bash
# 首选：重新 add —— 实测 update 补不上本包新增的入口技能
npx skills add <解析到的仓库地址> -y
# 只更新已装技能（不补新增）：
# npx skills check && npx skills update -y
```

> **实测结论**：`npx skills update` 只 "Checking N skill(s)"，**不会安装新增技能**；
> 从本地路径安装的技能无法 update（CLI 只认 git / 远程源）。
> 刷新失败**如实报告并停下**，不得假装已更新。

刷新后重读 `VERSION` 与新 `SKILL.md`；若版本高于正在运行的说明，按**新版说明**继续。

## Step 2: 替换式升级共享工作台（②）

一律走脚本，不手拍：

```bash
python3 <apply-design-skills 技能目录>/scripts/render-design-package.py \
  --project <当前项目根目录> --scope user
```

- 省略 `--disciplines` 时**读已有 `~/.design/design.json` 的工种集合**，保持用户当初的选择；
- 脚本内置：暂存树构建 → 逐字保真核对 → `verify-render.py` 结构校验 → 整体替换；
- `artifacts/` 原样保留，旧 `~/.design/` 先备份到 `~/.design.bak/`（成功后才删）；
- 测试想用临时主目录：加 `--home <临时目录>`，不会碰真实 `~/.design/`。

### 管理区 / 用户区（升级契约）

| 类别 | 路径 | 升级时 |
|---|---|---|
| 管理区（生成物） | `~/.design/rules/`、`templates/`、`references/`、`skills/`、`design.json`、`disciplines.json`、`README.md` | 可整体重建 |
| **用户区（作品）** | **`<当前项目>/.design/artifacts/`** | **绝不覆盖、绝不删除** |

> 用户几个月的设计稿全在 `artifacts/` 里，这是升级最容易出事的地方。**不要绕过脚本手拍。**

## Step 3: 扫描并对账注册（③）

```bash
python3 <install-design-skills 技能目录>/scripts/reconcile-skills.py --scope user
```

- **按工具真实规则探测**：先找本机用户全局目录下有哪些工具根（`~/.workbuddy`、`~/.codex` 等），
  只向检测到的工具目录建软链；未检测到的一律不创建（只用 WorkBuddy 时绝不出现 `~/.agents/`）；
- 期望集合 = `~/.design/skills/` 当前技能 + **三个公开入口命令**；不在集合内的本包项删除（清孤儿）；
- 用户自己放进工具目录的技能**一律不碰**；
- 清单 `.design-managed.json` 与各包互不干扰（`shuhe-role-skills` 用 `.roles-managed.json`）；
- `--home <临时目录>` 可隔离测试，不碰真实全局目录。

## Step 4: 校验与一句话汇报

校验：`~/.design/design.json` 版本已是新版本 / 每个工具目录技能数与 `~/.design/skills/` 一致、
无孤儿无断链 / 用户现有项目的 `artifacts/` 一个 dossier 都没少。

**成功更新后只输出一句**，例如：

```text
已从 1.0.0 更新到 1.1.0：本次新增了 3 个设计工种与深色模式检查表，原有设计稿已保留，重启会话后生效。
```

规则：从新版 `CHANGELOG.md` 提炼**一个**最主要变化；一句内包含版本变化、主要更新、是否需重启；
不贴完整变更清单或长表格；备份路径、异常与失败原因不受此限制，**必须如实说明**。

## 约束

- ❌ **绝不删除或覆盖 `<当前项目>/.design/artifacts/`**
- ❌ 不降级；版本未知不编造；仓库地址未知不编造
- ❌ 不写工具根目录本身、不写 `~/.codex/skills` 这类旧版目录
- ❌ 不向未检测到的工具目录写任何东西、不创建无关目录
- ❌ 不替用户选更新范围——列选项让他选（全走 / 只② / 只③ / 只看不动）
- ❌ 换工种集合前必须二次确认
- ✅ 同版本 = 不写文件（幂等），除非用户明确要求强制重渲染
- ✅ 升级共享工作台一律走渲染脚本
- ✅ 三个公开入口命令默认一并重新注册
- ✅ 更新完说明「重启会话后生效」
