# 循环引擎（自动推进）

> **作用域**: 工种无关的引擎。所有工种的自包含技能包都带这一份（可被工种同名覆盖）。
> **状态**: 强制
> **一句话**: 循环负责"按流程往下走"，人工门禁负责"该停就停"——**两者不冲突**。

---

## 0. 为什么需要循环

靠人记着"下一步该干嘛"，结果就是漏步、跳步、停在半路。循环引擎把"下一个阶段是什么、什么时候必须停"从人脑里搬进驱动卡。

**参照**：`huazai-harness-skills` 的 `harness-loop-run`——它每个 stage 派 fresh subagent、由状态文件驱动向下，并且**在需要人类审批时立即停机交还**。本引擎同构，但阶段清单来自本工种自己的入口技能。

---

## 1. 真相源：驱动卡（只信文件）

- 唯一状态来源：`.design/artifacts/<feature-slug>/00-summary.md` 的 frontmatter `status` 与「阶段状态表」。
- **只信文件，不信口头汇报**：子智能体返回后，必须重读驱动卡与产物 frontmatter，再决定下一步。
- 阶段清单来自**本工种入口技能的流水线表**，不要另造。

---

## 2. 循环怎么走（逐个循环轮次）

1. 读驱动卡 `status` 与「阶段状态表」，取**下一个未 confirmed 的阶段**；
2. 取不到 → 转 §4 收口；
3. 派 **fresh subagent** 执行该阶段技能（带**上下文指针**：文件路径 + 要读什么，**不塞正文、不带主会话历史**）；
4. 子智能体返回 → **重读产物 frontmatter 与驱动卡**（不看它的自述）；
5. 跑该阶段出口门禁：产物齐全 + 来源已列 + 门禁红线逐条核对；
6. 门禁不过 → **退回该阶段重跑**（不跳级），退回原因写进驱动卡；
7. 门禁通过 → 阶段置 `confirmed`、写驱动卡 → 进入下一个循环轮次。

> 循环是**阶段级自动推进**；阶段内部的问答仍是决策树迭代（见《交互模式》§4）。

---

## 3. 什么时候必须停（停机条件）

| # | 停点 | 动作 |
|---|---|---|
| 1 | `analyzing → producing`（简报确认） | 出结论卡 → 请人拍板 → **停** |
| 2 | `reviewing → confirmed`（最终产物确认） | 交人审核 → **停** |
| 3 | 范围变更 / 重大取舍 / 需发明业务规则 / 需对外承诺 | 列候选 → 请人决定 → **停** |
| 4 | 缺前置（无需求、无规格、无来源） | 输出缺什么、找谁要 → **停** |
| 5 | 不可逆或破坏性操作 | 先要授权 → **停** |
| 6 | 到达预算 / 循环上限 | 输出进度与剩余 → **停** |
| 7 | 同一阶段连续 2 次修不过 | 输出阻塞原因 → **停** |

> **停机不是失败**，它是循环的正常出口之一。宁可停下交还人类，也不要"猜着往下走"。

---

## 4. 收口（定义在别处，这里只交接）

**收口怎么做不在这里重复**——统一见 `{{DESIGN_ROOT}}/rules/状态机与收口.md` §11（汇总收口）与 §11.2（交付前四步）。

循环引擎在这里只做一件事：**把 `status` 推到 `reviewing`，然后停机**，等 §11.2 走完、人拍板。

---

## 5. 派发纪律

- **fresh subagent**：每个阶段一个新上下文，不复用上一个阶段的子智能体；
- **上下文指针**：给文件路径与"读哪些"，不把正文塞进派发指令；
- **返回后重读状态**，不信自述；
- **禁止无限循环**：必须有预算（时间 / 轮次上限），到点就停；
- 子智能体**不得代替人拍板**，不得宣布"可发布/可上线"。

---

## 6. 红线

- 不得跳过人工审批点（§3 第 1/2/3 条）直接往下走。
- 不得在出口门禁未过时推进 `status`。
- 不得信任子智能体的口头汇报——**只认文件**。
- 不得在没有预算上限的情况下无限循环。
- 不得把"停"包装成"完成"。
