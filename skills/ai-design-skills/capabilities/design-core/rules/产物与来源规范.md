# 产物与来源规范

> **作用域**: 工种无关。所有工种的自包含技能包都带这一份（可被工种同名覆盖）。
> **状态**: 强制

---

## 1. 产物头部（每个产物都有）

产物**以 frontmatter 开头**，机器可读，用于断点续传与状态总览：

```yaml
---
role: <工种 key>
feature: <特性 slug>
artifact: <产物名>
status: draft | proposed | reviewing | confirmed | delivered
version: v0.1
created: <日期>
---
```

`status` 分两层，不要混用：

| 层 | 载体 | 状态机 | 说明 |
|---|---|---|---|
| **dossier 驱动卡** | `00-summary.md` | 六态：`draft / analyzing / producing / reviewing / confirmed / delivered` | 驱动整条流水线，定义与硬规则见《状态机与收口》§11.1 |
| **单个产物** | 其余产物 | 五态：`draft / proposed / reviewing / confirmed / delivered` | 本节下方定义 |

**两层怎么对应（避免撞名歧义）**：

| dossier 驱动卡 | 含义 | 对应单产物 `status` |
|---|---|---|
| `draft` | dossier 建立、未开始 | `draft` |
| `analyzing` | 收敛完成、待人确认 | `proposed` |
| `producing` | 简报已确认、生产主产物 | `draft`（生产中的各产物） |
| `reviewing` | 主产物完成、提交评审 | `reviewing` |
| `confirmed` | 人确认最终产物 | `confirmed` |
| `delivered` | 已交付 | `delivered` |

> **以驱动卡为准**：流水线的阶段推进**只读 dossier 驱动卡 `00-summary.md` 的 `status`**（见《状态机与收口》§11.1）。
> 单产物 `status` 只标注**单个文档自身**的成熟度，不驱动阶段切换——两者都写，但决策看驱动卡。

单个产物的 `status` 含义：

| 状态 | 含义 |
|---|---|
| `draft` | 生产中 |
| `proposed` | 已完成、待人类确认（简报类 / 收口类产物） |
| `reviewing` | 已提交评审，等结论 |
| `confirmed` | 已由人确认，可被下游阶段引用 |
| `delivered` | 已交付（对外提供 / 进入下一环节） |

> **状态写在文件里**——新会话读 status 就知道当前在哪一步，不需要重新判断。
> **所有产物模板必须带本 frontmatter**（含 `status`）；产物创建时置 `draft`，收口类产物置 `proposed` 等人确认，人确认后改 `confirmed`，下游阶段才允许开始。

正文头部只保留人类可读的创建日期与版本：

```markdown
**创建日期：** <日期>　·　**版本：** <版本>
```

不得自动写入公司、产品名、责任人、术语表等组织信息。具体产物确有必要时，由用户提供后再写；没有来源就不写，**绝不编造看起来真实的值**。

## 2. Dossier 结构

同一特性的所有产物归入同一个 dossier：

```text
{{ARTIFACT_DIR}}<feature-slug>/
├── 00-summary.md          ← 汇总收口（对话结束时的结论卡片）
├── sources/               ← 原始素材（原样存档：口述 / 截图 / 聊天记录 / 旧文件）
├── 01-<artifact>.md
├── 02-<artifact>.md
└── ...
```

- 产物前缀按**生成顺序**编号。
- 宿主支持建目录时使用上面的结构；只能交付单文件时用 `<feature-slug>-NN-<artifact>.md` 命名兜底，**不要因为环境不支持目录就停在半路**。

### 恢复而非重问

开始新产物前先查找已有 dossier：

- 能找到 → 读它的 `status` 与已确认项，复用表头与编号，**不重复访谈**。
- 找不到 → 新建，并与用户确认目录名。

## 3. 字段来源标记

产物中每个关键字段标注来源：

| 标记 | 含义 | 能否视为已确认 |
|---|---|---|
| `[原文]` | 直接来自用户提供或可追溯的材料 | ✅ |
| `[推断·待确认]` | 推断，用户已确认 | ✅ |
| `[默认值·可否决]` | 采用安全默认，用户尚未否决 | ⚠️ 需确认 |
| `[缺失·阻塞]` | 缺失且阻塞 | ❌ 必须先补 |

只有 `[原文]` 和经确认的 `[推断]` 可以标 `confirmed`。

示例：

```markdown
| 字段 | 内容 | 来源 |
|---|---|---|
| 目标用户 | 首次下单的新用户 | [推断·待确认] |
| 积分获取规则 | 下单 100 元 = 10 积分 | [原文] 2026-10-26 会议记录 |
| 留存目标 | ??? | [缺失·阻塞] |
| 积分有效期 | 12 个月 | [默认值·可否决] |
```

## 4. 命名规范

- 文件名：小写 kebab-case，`.md` 结尾，不写中文空格与特殊符号。
- 每个工种使用**固定的产物名**——清单见本工种入口技能的「产物与状态」表；模板在 `{{DESIGN_ROOT}}/templates/` 下按需取用，不随意发明新文件名。
- 需要新产物时：**先加模板并登记**，再在技能里引用；模板是可选脚手架，产物名以工种流水线表为准。
- 变更类产物带版本或日期后缀，如 `requirement-change-v2.md`。

---

## 5. 归档

- `{{DESIGN_ROOT}}/design.json` 记录本包版本、本次启用的工种与产物目录，不记录公司、产品、责任人、术语表；
  完整工种清单在 `{{DESIGN_ROOT}}/disciplines.json`。
- 产物应可提交进 Git，作为决策留痕。
- 产物是**给用户拿出去的文档**——它要能脱离本工具独立阅读，不依赖只有 AI 才懂的上下文。

## 6. 原始素材存档（对话即来源）

> **前提**：本包装在**项目目录**级，而那个目录**可能是空的**——需求在用户脑子里、在聊天记录里、在别的系统里（原型链接 / Excel / 在线文档）。
> 所以：**「项目里没文件」不等于「没有来源」。** 空目录时，**对话就是唯一的来源入口**。

### 6.1 三类来源都要认

| 类型 | 例子 | 怎么处理 |
|---|---|---|
| ① 项目里的文件 | 需求文档、原型图、旧用例表 | 读它，登记路径 |
| ② **对话里给的** | 口述、粘贴的聊天记录/会议纪要、截图、贴的表格 | **原样存档**，登记日期与谁给的 |
| ③ 外部系统 | 原型/设计稿/在线文档的链接 | 能拿到就存「链接 + 取的日期」；拿不到记进「待补来源」 |

### 6.2 存放位置

原始素材一律进 `sources/`，**与加工产物分开放**：

```text
<feature-slug>/
├── sources/
│   ├── 原话-2026-11-05.md          # 用户口述，逐字
│   ├── 聊天记录-2026-11-05.md
│   ├── 原型截图-2026-11-05.png
│   └── 旧用例-来自Excel-2026-11-05.md
├── 00-summary.md
└── 03-test-cases.md                # 加工产物
```

### 6.3 存档三要素（缺一不可）

1. **原样**——逐字保存，**不总结、不改写、不美化**（要加工另开产物）；
2. **出处**——谁给的 / 从哪来（人名、渠道、链接）；
3. **日期**——收到的当天。

> 用户在对话里说的，**默认就要存**；不确定要不要存时，**存**（宁可多存，也不要第二天什么都没有）。

### 6.4 空目录的首次会话：必须有最小产出

哪怕用户只说了一句话，也要落这两样——否则第二次开会话就「什么都没了」：

- `00-summary.md`：目标 / 非目标 / 待确认项；
- `sources/原话-<日期>.md`：他说的原样存下来。

### 6.5 待补来源清单

拿不到的材料（例如「没有需求文档」）→ 记进驱动卡 `00-summary.md` 的**待补来源**，写清**找谁要、要什么**；下次会话继续挂着，不丢。

### 6.6 与字段来源标记的关系

产物里的关键字段用 `[原文]` / `[推断·待确认]` / `[缺失·阻塞]` 标注（见 §3）；
其中标 `[原文]` 的，**必须能指回 `sources/` 里的某一条存档**——指不回去的，就不是 `[原文]`。
