# 工种通用流水线（长尾工种兜底）

> **作用域**：`extended` 工种（`design-any` 技能）的展开说明；`/design-router` 分流时也可参考。
> 方法论借鉴 `julianoczkowski/designer-skills`（Apache-2.0）的「先盘问、再简报、再结构化」顺序，
> 以及 `full-stack-skills/design-skills`（Apache-2.0）的契约式产出思路；文字与模板均未搬运。

## 为什么需要一条通用流水线

全行业 37 个工种里，18 个属于长尾：要么低频，要么强依赖 CAD / 打样 / 材料 / 资质。
给它们各做一个技能会带来两个问题：

1. **命令爆炸**：30+ 斜杠命令的触发词互相抢，用户反而找不到该用哪个；
2. **假交付**：AI 给不出施工图、打样件、可印制原文件，做成「完整技能」等于承诺了做不到的事。

所以做法是：**清单收录 + 通用流水线兜底 + 明确边界**。覆盖到了，也不撒谎。

## 8 步（与 `design-any` 的流水线表一一对应）

### 0. 确认现状（硬门禁）

先问「最终要交出什么、给谁用」。按域补问：

| 域 | 补问 |
|---|---|
| 空间与实体 | 场地 / 尺度 / 材料 / 工艺 / 法规与资质 |
| 产品与工艺 | 人机尺寸 / CMF / 模具、版型、镶嵌约束 |
| 平面长尾 | 媒介 / 尺寸 / 色彩模式 / 出血 / 字体授权 |
| 影视与舞美 | 镜头 / 场景清单 / 置景预算 |

拿不到就停，不 best-guess。

### 1. 目标与约束

写清功能目标、受众、禁限项、预算与工期。**没有的一律标 `[缺失·阻塞]`**，不编数字。
把「好看、大气、有质感」这类不可验证表述退回重写成可判断的目标。

### 2. 参考与竞品

至少 3 个可核对的参考，每条记**出处 + 日期 + 借什么**。不编案例、不写「业内通常」。
参考稿只在本次项目内使用，不外传。

### 3. 结构 / 层级方案

把对象拆成可讨论的结构（空间拆动线与功能区、印刷拆信息层级与栅格、产品拆部件与工艺）。
每个结构块要能回指第 1 步的目标，对不上就说明是装饰而非必要。

### 4. 方向提案（2–3 个）

给**真正不同**的方向，差异必须在「结构 / 叙事 / 工艺路径」上，不是换套配色。
每个方向写清取舍与风险，别只说优点。

### 5. 收敛

用户选方向后才深化。沿决策树一次一问，收敛时对话内出结论卡片 → 落盘 `00-summary.md`
（`status: analyzing`）→ **用户确认后才改 `producing`**。

### 6. 规格与检查清单

尺寸、材料 / 工艺、标注、验收口径、风险。每条可验证。
涉及界面时补 8 类状态（默认 / 加载 / 空 / 单条 / 极多 / 超长 / 错误 / 权限不足）。

### 7. 交付与交接

明确列出「本次交付了什么」与「还需谁用什么软件接手」。
**禁止**把方案文档说成已完成实体设计交付。

## 边界声明模板（第 0 步必须贴出来）

```text
「<工种>」属于长尾工种，本包没有专属流水线，我按通用设计流水线走。
我能给你：需求简报、参考与竞品分析、方案方向、规格与检查清单、可评审文档。
我不能给你：施工图 / CAD / BIM、打样件、可印制原文件、材料与结构验算、资质报审。
这些必须交给对应专业的从业者或软件完成。
```

## 什么时候不要走通用流水线

- 用户描述的工作其实命中某个 `core` 工种 → 指回对应技能；
- 一次涉及多个工种 → `/design-router` 拆分；
- 用户要求实体交付物 → 直接说明做不到，别绕一圈再拒绝。
