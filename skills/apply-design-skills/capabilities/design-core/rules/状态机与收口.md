# 状态机与收口

> **作用域**: 工种无关的引擎。所有工种的自包含技能包都带这一份（可被工种同名覆盖）。
> **状态**: 强制
> **编号说明**: 本节**沿用《交互模式》的 §11 编号**——所有「引擎 §11 / §11.1 / §11.2」的引用都指向本文件。
> **相关**: 自动推进见 `{{DESIGN_ROOT}}/rules/循环引擎.md`；双轴独立评审见 `{{DESIGN_ROOT}}/rules/评审子智能体.md`。

## 11. 汇总收口（对话是主体，产物是钥匙）

当决策树收敛、本轮问答结束时（不是随时），按三步收口：

1. 对话内输出**结论卡片**——固定结构、直接贴在对话里；
2. **落盘**：写入 dossier 的驱动卡 `00-summary.md`，frontmatter `status: analyzing`（收敛完成、待人确认）；
3. **明确提示"请确认"并停下**。人类确认 → 驱动卡 `status` 改 `producing`，才写后续产物、才进入生产阶段。

```markdown
## 本轮结论

| 维度 | 内容 |
|---|---|
| 核心目标 | ... |
| 非目标 | ... |
| 目标用户 | ... |
| 成功标准 | ... |
| 关键约束 | ... |
| 已确认 | ... |
| 待确认 | ... |
| 下一步 | ... |
| 本次新增来源 | 口述/粘贴/截图 存进了 `sources/` 的哪几条（没有就写「无」） |
```

**不得跳过收口直接产出完整产物；人未确认不得擅自推进状态。**

**收口前不预告**（防「一把梭」的关键）：收敛之前——不出结论卡、不列默认值表、不预告全量交付清单。这些**全部属于收口**，只在此处出现一次。第一个问题就出现它们，等于把一堆决策一次性倒给用户。

## 11.1 状态机与阶段门禁（线性主干 + 门禁回退）

仿 Harness 变更状态机制定，**机器门禁（CI/hooks）替换为人工确认**：一个 dossier 一条状态线，写在驱动卡 `00-summary.md` 的 frontmatter `status`，全程驱动流水线。

```text
draft → analyzing → producing → reviewing → confirmed → delivered
          ↑____________|          ↑___________|
              打回                    打回
```

| 状态 | 含义 | 谁推进到这里 |
|---|---|---|
| `draft` | dossier 建立，未开始 | AI 创建时 |
| `analyzing` | 问答收敛**完成**、收口卡完整、**待人确认** | AI 收敛时（收敛*过程*是决策树迭代，不单独占状态） |
| `producing` | 简报已确认，生产主产物（工种流水线主阶段） | **人类确认后**（AI 不得擅自推进） |
| `reviewing` | 主产物完成，提交评审 | AI 提交时 |
| `confirmed` | 人确认最终产物——**进入下一环节的唯一钥匙** | **人类确认后** |
| `delivered` | 已交付（对外提供 / 进入下一环节） | AI |

硬规则：

- **线性主干**：阶段严格按序，不跳步；**任一出口门禁不通过 → 退回修复或请示人类，禁止进入下一阶段**。
- **门禁回退**：打回时按问题性质回退到对应上游状态（不跳级），并在驱动卡记录原因——简报被打回回 `analyzing`，产物被打回回 `producing`。
- **人类审批点**（AI 不得擅自推进）：① `analyzing → producing`（简报确认）② `reviewing → confirmed`（最终产物确认）③ 范围变更 / 重大取舍。
- **断点续传**：状态写在文件里——新会话读 `status` 就知道当前在哪一步，不重复访谈。
- **多 dossier 并存**：显式指定 `<feature-slug>` 优先；多个候选时**停下列出清单请人类选择**，禁止擅自默认取第一个。

> **线性指阶段级**；阶段内部（如问答收敛）是决策树迭代，不是线性。合起来是"线性主干 + 门禁回退"，不是单调向前。
>
> 工种流水线的具体阶段映射到本状态机：收集/简报 = `analyzing`，主产物生产 = `producing`，评审 = `reviewing`，人确认 = `confirmed`，交付 = `delivered`。

### 自动推进：循环引擎

阶段之间**自动推进**由《循环引擎》负责：读驱动卡取下一个未完成的阶段 → 派 fresh subagent 执行该阶段技能 → 返回后**重读产物状态**（不信自述）→ 跑出口门禁 → 过了才推进。

**推进过程中遇到下列情况必须停机交还人类**（不是失败，是循环的正常出口）：

1. `analyzing → producing`（简报确认）；
2. `reviewing → confirmed`（最终产物确认）；
3. 范围变更 / 重大取舍 / 需发明业务规则 / 需对外承诺；
4. 缺前置（无需求、无规格、无来源）；
5. 不可逆或破坏性操作（需先授权）；
6. 到达预算 / 循环上限；
7. 同一阶段连续 2 次修不过。

> **自动推进 ≠ 自动放行**：循环照走，审批点照停。详见 `{{DESIGN_ROOT}}/rules/循环引擎.md`。

## 11.2 自检 · 独立评审 · 用户审核 · 意见回退重跑（每个工种收尾必走）

**交付前按顺序走这四步，不得跳。** 这是"最终给的"和"一开始说的"不出错的唯一保障。

> 第 1 步是**作者视角**，第 2 步是**独立视角**——两者必须是两个上下文，见《评审子智能体》。
> **主会话自审不算独立评审。**
>
> **第 2 步是否适用由工种决定**：工种在自己的评审清单里声明是否启用评审。**启用了就必须走第 2 步**；
> 未启用的工种可跳过第 2 步，但必须**在驱动卡显式记录"本工种不设独立评审"及理由**，不得静默跳过。

### 第一步 · AI 自检（对照"最初说的"和"最后给的"）

产出完成后、交给人之前，**先自己跟最初的规格和沟通过程对一遍账**，专门找**漂移**：

| 对账 | 找什么 |
|---|---|
| 最终产物 ↔ 第 0/1 阶段确认的规格 / 简报 | 有没有**多做的、漏做的、改口的** |
| 最终产物 ↔ 沟通过程中的关键决定 | 用户中途定的取舍（范围、指标、方向）有没有落实 |
| 产物 ↔ 产物 | 前后一致：数字、命名、范围、术语不打架 |
| 产物 ↔ 门禁 | 该工种红线逐条是否满足 |

- 有偏差 → **先修**；修不了的**显式列出**请用户裁决，**不许带病交付**。
- 自检结论写进驱动卡 `00-summary.md` 的「AI 自检」表，**不要只在对话里说**。

### 第二步 · 独立评审（双轴，见《评审子智能体》）

由**不共享本次上下文**的评审者，按本工种的评审清单派发**双轴**评审：

- **Spec 轴**：对照本工种的规格来源（需求 / AC / 简报 / 接口文档…），查"该做的做了吗、有没有做不该做的"；
- **Standards 轴**：对照本工种的规范与门禁，查合规与红线。

规则（详见《评审子智能体》）：

- 两轴**独立运行、互不可见**，报告**不合并不排序**，分 `## Spec 轴报告` / `## Standards 轴报告` 两节原样呈现；
- 子智能体**只读**，不得改产物、改代码；
- 宿主无子智能体原语时，降级为**另开新会话**顺序两遍，并**必须标注「降级模式」**；
- 每条 🔴 必须带引用（产物章节 / 条款 / 用例号）；**0 个 🔴 才可进入用户审核**；
- 结论写进驱动卡 `00-summary.md` 的「独立评审」表。

### 第三步 · 用户审核

把产物交给用户（关键内容已按 §10 展示在对话里），**明确请其逐条给意见**，并停下等待。

### 第四步 · 用户有意见 → 状态回退 + 重跑

用户提意见，**不是"顺手改一下"**——按性质回退到对应状态，走状态机重跑：

| 意见性质 | 回退到 | 重跑什么 |
|---|---|---|
| 目标 / 范围变了 | `analyzing` | 重走简报 → 确认 → 生产 |
| 主产物要改 | `producing` | 重做产物 |
| 评审结论要改 | `reviewing` | 重新评审 |
| 只是措辞 / 格式 | 留在当前阶段 | 改完**重新自检** |

硬规则：

- **回退要留痕**：在驱动卡记「回退到哪 + 原因 + 日期」，写不清就不算回退。
- 有 🔴 的产物，**先按独立评审报告修**，再重新自检、重新派发独立评审。
- **重跑后重新自检 + 重新请用户审核**，直到用户确认。
- 用户确认后才 `confirmed`，才允许进入下一环节。
- 打回**不跳级**（见 §11.1），按问题性质回到对应上游。

> 一句话：**"改了" 必须能在驱动卡上看出"从哪退回、改了什么、又确认过"。**
